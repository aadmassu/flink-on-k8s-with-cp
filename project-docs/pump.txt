KEY JUSTIFICATION — A KAFKA BROKER EXPOSES MULTIPLE LISTENERS, EACH WITH A DIFFERENT AUTHENTICATION PROFILE

A single Apache Kafka broker can (and at FCB must) bind multiple TCP listeners, each on a distinct port and each carrying a different SASL or TLS authentication mechanism. This is a core feature of the Apache Kafka broker, configured via `listeners` + `listener.security.protocol.map` on the broker process and surfaced on the CFK `Kafka` CR's `spec.listeners` block. The architecture is not a workaround; it is how every production Kafka cluster supports heterogeneous client populations.

At FCB the Kafka CR (apps/confluent-platform/<env>/kafka.yaml) declares three listeners:

  - internal     — SASL_SSL with PLAIN auth          — broker-to-broker only, on TCP/9091, never crosses the perimeter
  - external     — SASL_SSL with OAUTHBEARER (Okta)  — primary client-facing listener used by every CFK component, every Flink job, and downstream microservices for OAuth-authenticated produces/consumes — on TCP/9092
  - certonly     — SSL with mTLS                     — cert-only listener for clients that authenticate by client certificate rather than by OAuth token — on TCP/9094

These are not three different services; they are one Kafka broker process binding three TCP ports. Each external listener serves a different client persona:

  - OAuth clients (DAH apps and downstream consumers using Okta-issued tokens) connect to 9092
  - mTLS clients (the active VM CP cluster-link source broker during the VM CP -> CFK migration window; mTLS-only integration tooling using Keyfactor-issued client certificates) connect to 9094

The two listeners cannot be collapsed onto a single port because the listener's authentication and TLS-handshake behavior is bound per-port in the broker's listener.security.protocol.map. Removing 9094 also removes the entire mTLS auth path, which is the only way the cluster-link source broker (still on VM CP today) is configured to authenticate to the destination during migration.

WHY NOT TCP/443

Kafka uses a binary wire protocol over a long-lived TCP socket, framed inside TLS. It is not HTTP. HAProxy on FCB's Core Zone ingress routers decodes HTTP/1.1 / HTTP/2 / HTTPS at Layer 7 to route requests; Kafka traffic carries no HTTP envelope and cannot be routed by HTTP-aware proxies. The only HAProxy mode that passes Kafka through is `route.openshift.io/termination: passthrough` with SNI-based routing, and that lands the client on TCP/443 — preserving the port part of the problem this exception is meant to solve.

A practical consequence: every existing FCB Kafka client (VM CP cluster-link, mTLS-only producers, downstream consumers) is configured against bootstrap.servers on TCP/9092 (OAuth) or TCP/9094 (mTLS), with Keyfactor / Okta credentials issued under SANs that cover the broker hostnames on those specific ports. Moving the listener to TCP/443 requires re-issuing every client certificate (SAN re-issuance through Keyfactor) and reconfiguring every client's bootstrap.servers — a multi-team coordination across DAH, downstream consumers, and the active VM CP cluster-link mirror — for no platform-side gain.

For the seven non-broker CP services (Schema Registry, Connect, REST Proxy, MDS, Control Center, CMF, Flink JobManager) — all of which speak HTTP/HTTPS — we ARE migrating to TCP/443 Ingress mapped to each service's native backend port (8081 / 8082 / 8083 / 8090 / 9021 / 8080 / 8081). That decision was locked in at Friday's walk. The custom-port exception requested here is scoped only to the Kafka wire protocol, which is binary not HTTP.

ALTERNATIVES CONSIDERED

- TCP/443 Ingress via HAProxy: not viable for Kafka (binary wire protocol; not HTTP). Even with passthrough, lands clients on TCP/443 — defeats migration transparency and breaks cluster-link.
- OpenShift Route with TLS passthrough: same as above; lands on TCP/443.
- NodePort Service: prohibited by FCB platform admission control policy (Rick confirmed Friday — admission control rejects services attempting to expose NodePort).
- LoadBalancer Service: contradicts the FCB ClusterIP-only Services standard.

The non-standard custom-TCP-port request form is the only path that preserves: (a) the standard Kafka multiple-listener architecture, (b) compatibility with existing FCB Kafka clients without re-issuing their TLS certificates, and (c) the active VM CP cluster-link mirror dependency during the migration window.

TLS REQUIREMENT

Both 9092 and 9094 terminate at the broker's Keyfactor-issued TLS server certificate, with per-broker SAN entries covering the per-broker DNS hostnames. No unencrypted traffic is exposed on either port:

  - 9092 — wire-protocol TCP, encrypted via the SASL_SSL listener's TLS layer; OAuth bearer token enveloped inside
  - 9094 — wire-protocol TCP, encrypted via the SSL listener's TLS layer; client presents a matching mTLS client certificate at the TLS handshake

Both meet the FCB requirement that all exposed services use TLS certificates and that no unencrypted connections are allowed.
