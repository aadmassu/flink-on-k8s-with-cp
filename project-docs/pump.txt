What the docs say (the discovery)
---------------------------------
https://docs.confluent.io/operator/current/co-security-compliance.html
#deploy-cp-in-the-fips-mode

Key claims, verbatim:

  "Confluent Server (Confluent Kafka), KRaft, Schema Registry, Connect, and
  ksqlDB require FIPS-compliant Java KeyStore type, Bouncy Castle"

  "Bouncy Castle keystores (BCFKS) are required for FIPS-compliant TLS
  connections"

  The component Secret must contain:
    keystore.bcfks
    truststore.bcfks
    keystore.jks
    truststore.jks
    jksPassword.txt

  Documented CR field path:
    spec:
      tls:
        fips:
          enabled: true
          mode: <fips-mode>   # Optional, CFK 3.2.0+
        secretRef: <secret-name>

The gap
-------
- The kafka-tls Secret currently contains: tls.crt, tls.key, ca.crt (from
  Keyfactor via cert-manager); keystore.jks + truststore.jks (from the
  keystores.jks Certificate block we added in commit 502cea5). It does NOT
  contain BCFKS material.
- cert-manager 1.x's keystores block only emits JKS and PKCS12 -- no
  BCFKS support upstream. There is no in-cluster tool in our namespace that
  produces BCFKS from PEM material.
- Therefore: we cannot satisfy the operator's FIPS-strict validator from
  the Kafka CR alone, regardless of how many keys we pre-render. The
  "missing value" error message reads literally but more accurately means
  "the truststore location must resolve to a BCFKS file at a path the
  validator recognizes".

Two options for the dev install
-------------------------------
(1) Provision a BCFKS conversion sidecar/Job in dah-flink-dev (or in
    confluent-operator as a namespace-scoped utility). On each kafka-tls
    Secret rotation the Job reads tls.crt/tls.key/ca.crt, converts to
    BCFKS via the BouncyCastle CLI (bc-fips jar + keytool), patches the
    Secret with keystore.bcfks + truststore.bcfks. Same for any other
    component Secret that needs FIPS material (kraftcontroller-tls,
    schemaregistry-tls, etc.). Right long-term shape for stg/prd too.
    Effort: ~30-60 min infra work + base image with bc-fips and keytool.

(2) Disable fipsmode=true on the dev CFK operator install:
        helm upgrade --reuse-values --set fipsmode=false \
          confluent-operator confluentinc/confluent-for-kubernetes \
          --namespace confluent-operator
    We keep spec.tls.fips.enabled=true on the Kafka CR (no-op when the
    operator isn't running the strict validator, but keeps the dev
    manifests aligned with what prod will look like once the BCFKS
    pipeline lands). Removes the immediate blocker. Loses the
    operator-attested FIPS validation path for dev only -- broker
    runtime FIPS posture is governed by the JVM bootclasspath and the
    cp-server image (artifactory.fcbint.net/.../cp-server:8.1.3), both
    unchanged. The brokers can still run BCFKS-format keystores at
    runtime if the image is configured that way; the operator just won't
    enforce it pre-deploy.

Ask
---
For dev only: which of (1) or (2) do you want us to go with? If (2), we
can re-install the operator ourselves once you bless the change, or you
can do it.

For stg/prd: BCFKS production is the right path regardless. If we go with
(2) for dev now, we'd still need to stand up the BCFKS conversion pipeline
before stg's CFK install. Happy to scope that as a follow-up once dev is
unblocked.
