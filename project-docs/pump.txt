SWEET32 / CVE-2016-2183 — BROKER REMEDIATION ACTION PLAN
================================================================================

Reply context: response to Anusha K.
Scope: The current vulnerability scan flagged the Kafka BROKER TLS
listener only. This plan addresses the broker. Other Confluent
Platform components (KRaft Controller, Schema Registry, Kafka Connect,
REST Proxy, Control Center) are NOT in scope for this report — each
would need its own analogous remediation if a future scan flags it.

Environment:
  - RHEL (8 or 9)
  - Java 21
  - Confluent Platform 8.x (likely 8.0)
  - KRaft mode (no ZooKeeper)


REVIEW OF THE PROPOSED 3-LAYER PLAN
================================================================================
The plan is correct and supported by Confluent. Three refinements
before execution:

1. JVM layer
   Java 21 already includes 3DES_EDE_CBC, DESede, RC4, and other
   legacy algorithms in the default jdk.tls.disabledAlgorithms list.
   The proposed change is largely audit-defensible policy rather than
   a behavioral change. Apply it via an override file referenced from
   KAFKA_OPTS, NOT by editing $JAVA_HOME/conf/security/java.security
   in place — JDK package updates silently revert in-place edits.

2. Application layer
   ssl.cipher.suites in Kafka is an ALLOWLIST using Java-style cipher
   names (e.g. TLS_ECDHE_RSA_WITH_AES_256_GCM_SHA384), NOT an
   OpenSSL-style denylist. Enumerate the ciphers you keep. Within the
   broker, the global ssl.cipher.suites can be OVERRIDDEN per listener
   via listener.name.<NAME>.ssl.cipher.suites — if you use prefixed
   listeners, set the allowlist on each variant.

3. OS layer
   Java does NOT follow the RHEL system crypto policy. The OS change
   only affects C-based tooling on the broker host (openssl,
   librdkafka clients, monitoring agents). RHEL 8/9 DEFAULT already
   excludes 3DES server-side; verify before tightening to FUTURE,
   which also drops SHA-1 and can break enterprise PKI interop.

No interference is expected with default broker listeners or
inter-broker replication, provided the rolling restart keeps the
allowlist consistent across all brokers.


RECOMMENDED CIPHER ALLOWLIST
================================================================================
Apply this value to every broker ssl.cipher.suites property (global
and any listener-prefixed variants). ECDHE + AES-GCM and ChaCha20
only — no CBC, no 3DES, no RSA key exchange, no static DH.

ssl.cipher.suites=TLS_AES_256_GCM_SHA384,\
TLS_AES_128_GCM_SHA256,\
TLS_CHACHA20_POLY1305_SHA256,\
TLS_ECDHE_ECDSA_WITH_AES_256_GCM_SHA384,\
TLS_ECDHE_RSA_WITH_AES_256_GCM_SHA384,\
TLS_ECDHE_ECDSA_WITH_AES_128_GCM_SHA256,\
TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256,\
TLS_ECDHE_ECDSA_WITH_CHACHA20_POLY1305_SHA256,\
TLS_ECDHE_RSA_WITH_CHACHA20_POLY1305_SHA256

ssl.enabled.protocols=TLSv1.3,TLSv1.2


================================================================================
GLOBAL — JVM (broker nodes)
================================================================================
Action:
  Add an explicit JDK security override file that pins the disabled-
  algorithms list on every broker node.

Reason:
  Java 21 already disables 3DES by default, but an explicit override
  file survives JDK upgrades and provides an auditable artifact.
  In-place edits of java.security are reverted by package updates.

How / where:
  1) Create /etc/confluent/java-security-override.properties on each
     broker node:

       jdk.tls.disabledAlgorithms=SSLv3, TLSv1, TLSv1.1, RC4, DES, \
           MD5withRSA, DH keySize < 2048, EC keySize < 224, \
           3DES_EDE_CBC, DESede, anon, NULL, \
           include jdk.disabled.namedCurves

  2) Reference it from the broker systemd unit (or sysconfig) via
     KAFKA_OPTS:

       Environment="KAFKA_OPTS=-Djava.security.properties=/etc/confluent/java-security-override.properties"

  3) Use single `=` (additive merge), NOT `==` (full replace).


================================================================================
GLOBAL — OS (broker nodes)
================================================================================
Action:
  Confirm the RHEL crypto policy on each broker host excludes Sweet32
  ciphers; tighten with a subpolicy if anything legacy is still
  negotiable.

Reason:
  Java ignores this policy, but any C-based tool on the broker host
  (openssl, librdkafka clients, monitoring agents) follows it.
  Closing the non-Java path completes the defense-in-depth picture.

How / where:
  Check current state:
    update-crypto-policies --show
    openssl ciphers -v 'ALL:!aNULL:!eNULL' | grep -iE '3des|des-cbc3'
       (should return nothing on RHEL 8/9 DEFAULT)

  Hardened baseline without breaking SHA-1 interop the way FUTURE does:
    update-crypto-policies --set DEFAULT:NO-SHA1:NO-3DES

  Restart non-Java services on the broker host after the policy change.
  The Kafka broker process is unaffected by the OS change alone.


================================================================================
BROKER
================================================================================
Config: /etc/kafka/server.properties

Action:
  Set ssl.cipher.suites and ssl.enabled.protocols on every broker. If
  the broker exposes multiple listeners (e.g. client, internal,
  external), apply the allowlist on each listener-prefixed variant
  as well. Confirm the listener named by inter.broker.listener.name
  is covered.

Reason:
  The broker is the surface flagged by the scan. The same listener
  config governs client traffic, inter-broker replication, and admin
  tooling — fixing the broker listeners closes all three paths.

How / where:
  Global default:
    ssl.enabled.protocols=TLSv1.3,TLSv1.2
    ssl.cipher.suites=<allowlist>

  Per listener (prefixed form wins over the global default):
    listener.name.<INTERNAL>.ssl.cipher.suites=<allowlist>
    listener.name.<EXTERNAL>.ssl.cipher.suites=<allowlist>
    listener.name.<INTERNAL>.ssl.enabled.protocols=TLSv1.3,TLSv1.2
    listener.name.<EXTERNAL>.ssl.enabled.protocols=TLSv1.3,TLSv1.2

  Inter-broker: confirm the listener name in
  inter.broker.listener.name matches one of the listeners above.

  Rolling restart: ONE broker at a time. Verify under-replicated
  partitions return to zero between each:

    kafka-topics.sh --bootstrap-server <host>:9093 \
                    --describe --under-replicated-partitions

  Output must be empty before restarting the next broker.


VERIFICATION
================================================================================
Per broker listener, after restart:

  # Should succeed — a modern ECDHE+GCM cipher negotiates:
  openssl s_client -connect <host>:<port> -tls1_2 \
      -cipher 'ECDHE-RSA-AES256-GCM-SHA384' </dev/null

  # Should fail — Sweet32-vulnerable cipher rejected:
  openssl s_client -connect <host>:<port> -tls1_2 \
      -cipher 'DES-CBC3-SHA' </dev/null

  # Full posture survey per listener:
  nmap --script ssl-enum-ciphers -p <port> <host>

Repeat for every TLS port the broker exposes.


DIRECT ANSWERS TO THE THREE QUESTIONS
================================================================================
Q1: Are these the recommended remediation steps for Confluent Platform
    to resolve CVE-2016-2183?

A1: Yes. Refinements: (a) apply the JVM change via an override file
    referenced from KAFKA_OPTS, not by editing java.security in place;
    (b) the application-layer cipher list is an allowlist using
    Java-style cipher names — enumerate the ciphers you keep; (c) the
    OS-level change only affects non-Java tooling on the broker host
    because Java does not follow the RHEL system crypto policy.


Q2: Are there any specific internal Confluent components that require
    additional configuration beyond the standard SSL properties?

A2: For the broker (the only component flagged in the current scan):
    inside a single server.properties, the global ssl.cipher.suites
    can be OVERRIDDEN per listener via
    listener.name.<NAME>.ssl.cipher.suites. If the broker exposes
    multiple listeners (client, internal, external), set the allowlist
    on every prefixed variant — the prefixed form wins over the global
    default. Inter-broker traffic uses the listener named by
    inter.broker.listener.name; confirm that listener is covered.

    Other CP components (Schema Registry, Kafka Connect, REST Proxy,
    Control Center) each have multiple SSL contexts of their own
    (listener side plus one or more embedded-client sides) that do
    NOT inherit from the broker config. None are flagged in the
    current report. If a later scan covers them, each will need its
    own analogous configuration.


Q3: Will these changes interfere with any default internal listeners
    or replication mechanisms if SSL is being used for inter-broker
    communication?

A3: No, provided every broker comes back with the same allowlist. The
    recommended ECDHE + AES-GCM list is supported by all CP 8.x
    brokers on Java 21, so inter-broker replication and admin paths
    continue to work unchanged. The only operational risk is the
    transient inconsistent state during a rolling restart — mitigate
    by restarting one broker at a time and confirming URP returns to
    zero between each.


PERFORMANCE
================================================================================
No regression expected. AES-GCM is hardware-accelerated on all modern
x86_64 CPUs (AES-NI). Removing 3DES-CBC removes the slowest cipher in
the negotiable set, not the fastest.


END OF PLAN
