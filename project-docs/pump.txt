REVISED THEORY: this is a semantic 404 from MDS, not a transport failure.
   * If it were transport (TCP or TLS), the operator's Go http client would

doesn't have an entry mapping our Kafka cluster to a resolvable ID/name.
Rolebindings use `kafkaRestClassRef.name: default` and rely on MDS to walk
KafkaRestClass -> Kafka CR -> cluster_id via that registry. If the registry
entry never got written, MDS can't resolve the target cluster and returns
Not Found for every rolebinding apply. Reasons the registry entry might be
missing:
   * MDS bootstrap didn't complete after Rick's fipsmode=false rollout
     (helm upgrade may have wiped in-memory MDS state on the operator side)
   * `_confluent-metadata` topic was never created because the broker's
     auto-topic-create failed (RBAC deny? replication factor mismatch?)
   * Cluster-registration step ran but errored silently

Also possible: MDS is initialized but the CFK operator's kafkaRestClassRef
resolution is doing something we don't expect (e.g., looking up the class
by a different name, or needing an additional field we haven't set).

THE MECHANISM GAP: spec.services.mds and a TOKEN listener at :9073 are
SEPARATE things.
   * spec.services.mds runs the MDS REST service at :8090 alongside the
     broker JVM. This is what CFK status reports as services.mds. Deployed.
   * TOKEN listener at :9073 is a Kafka SASL/OAUTHBEARER listener that
     clients (SR, Connect, C3) use when authenticating with MDS-issued
     bearer tokens. Never rendered into the broker's listeners=. Never
     opened.

The Kafka Service in ClusterIP does expose port 9073 (per diagnostics), so
Kubernetes will accept a connection on that port -- but the broker pod
isn't listening behind it, so the connection either times out or gets
Connection Refused depending on kube-proxy mode. That's why SR times out
on fetchMetadata against :9073 -- the port is advertised in DNS/Service
but not backed by a pod-level listener.

Why the render gap: candidate hypotheses (in decreasing order):
   1. spec.services.mds.authentication is a required field we didn't set.
      The CRD (checked at NR>=5666 in
      charts/confluent-for-kubernetes/crds/platform.confluent.io_kafkas.yaml)
      has spec.services.mds.authentication with enum type=[bearer] and
      required=[type]. Our current kafka.yaml is missing this field entirely.
      The operator's render logic for the TOKEN listener may key off it.
   2. spec.listeners.internal.authentication.type: plain (our current
      config) doesn't trigger the operator's auto-inject of a TOKEN
      listener sibling. If the operator only auto-adds :9073 when internal
      is already oauth-or-bearer-typed, we'd need to change internal to
      oauth (which would break the SR/Connect/KafkaRest PLAIN paths).
   3. CFK 3.2 render bug -- the operator STATUS-reports the TOKEN listener
      but never writes it into the broker config. Would need Confluent
      support to confirm and patch.

NEXT MOVE -- try (1) first, cheapest:

   spec:
     services:
       mds:
         tls: { enabled: true, secretRef: kafka-tls }
         tokenKeyPair: { secretRef: mds-token-keypair }
         authentication:                # <-- ADD THIS
           type: bearer
         provider:
           type: oauth
           oauth: { configurations: {...}, secretRef: oauth-mds-rest }

If iteration N+1 with this added to kafka.yaml re-runs install-or-update
and the broker's KafkaConfig values dump NOW shows TOKEN://:9073 +
TOKEN:SASL_SSL in the protocol.map + OAUTHBEARER mechanism, we've found
the trigger and this is a documentation-gap issue (not a bug). Move to

If the token listener is STILL absent after adding services.mds.authentication,
