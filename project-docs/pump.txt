Rick's round-2 guidance:
- ONE SNOW ticket per group of FQDNs (bundle them, don't split)
- Zscaler cares ONLY about the FQDN + port 443. Do NOT mention backend ports. It only confuses the Zscaler operator.
- Suggested we consider the "Floating DNS" pattern from OpenShift Ingress.pdf — <thing>.apps.dv.ocp.fcbint.net (no -p / -s), needs an extra DNS record but gives us identical FQDN shape across dev/qa/uat/prod and one-DNS-flip failover in UAT/Prod. Doc calls this "Optional, but recommended."
- "Do both, if you want" — i.e. whitelist both -p direct + floating. We decided NOT to do both (doubles whitelist / DNS / cert-SAN surface for zero gain in dev).

Decision landed on:
- Adopt floating for the five REST/UI components (controlcenter, schemaregistry, kafka-mds, kafkarest, connect) — stateless HTTP, no advertised-hostname baking, cheap to rename, wins consistency across all six envs.
- Keep the kafka broker on the direct name (kafka.apps.dv-p.ocp.fcbint.net) for now. Broker has an advertised-listener FQDN baked into the CFK Kafka CR spec.listeners.external; if bootstrap FQDN != advertised FQDN, clients get redirected to the -p name and if that's not also whitelisted the connection breaks. Also brokers don't fail over via DNS-flip so floating's benefit is smaller for the broker. Flagged this to Rick so he can weigh in.
- Ask Rick about the DNS-request path for the floating names in the same round-trip (SNOW DNS Request vs. lighter path since they share the same core-zone LB IP 10.7.72.209).
