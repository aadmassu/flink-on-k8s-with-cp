# CFK / CMF Per-Environment Deploy Checklist

Use this checklist for every env promotion (dev → qa → uat → prd → dr).
Copy the relevant section into a SNOW ticket or working notes; tick
items off as you go.

Living document. When `LESSONS_LEARNED.md` gains a new entry that implies
a new pre-flight check, add the corresponding line item here.

Pair this with `LESSONS_LEARNED.md` for the *why* behind each gate.

---

## 0. Pre-flight (platform-side, do not start until ALL of these pass)

These are not in our control; confirm with the named owner before
touching any manifests for the target env.

- [ ] **Namespace exists**: `dah-flink-<env>` is created and labelled per
      FCB standards. Owner: Tom (Container Platforms).
- [ ] **ResourceQuota sized for full CFK + CMF stack**: at minimum
      ~6 CPU / 24 Gi to fit 6 CFK pods (each claims ~500m via init
      container floor; see `LESSONS_LEARNED.md` A3) plus CMF. Owner: Tom.
- [ ] **`flink-operator` ServiceAccount pre-created** in the target
      namespace, with namespace-scoped Role/RoleBinding. Owner: Tom.
- [ ] **CFK operator running** and watching `dah-flink-<env>`. Owner:
      Container Platforms. Confirm the deployed operator version with
      Tushar; map build-number to CFK semver per the
      `[project-fcb-cfk-operator-ownership]` memory.
- [ ] **Ceph RBD CSI driver healthy on every worker** that may host CFK
      pods. Owner: Rick. (Bit us on dev; see `LESSONS_LEARNED.md` E2.)
- [ ] **ESO operator + namespaced SecretStore** pointed at CyberArk CCP
      and reachable from this namespace. Owner: shared (Tom for the
      SecretStore manifest, FCB Security for the CCP-side AppID allowlist).
- [ ] **All required CyberArk records exist** in the right safes:
  - [ ] CFK license JWT
  - [ ] CMF DB password (SQL Server)
  - [ ] CMF encryption key (**DO NOT ROTATE**)
  - [ ] OAuth client secrets per CFK component (one per CR)
  - [ ] MDS token keypair
  - [ ] SASL plain internal credentials
  - [ ] TLS cert material (if not generated by KeyFactor cert-manager)
- [ ] **Artifactory mirrors all required image tags**: confirm with
      Tushar that the env's pull-secret can reach `cp-server:8.1.3`,
      `cp-schema-registry:8.1.3`, `cp-server-connect:8.1.3`,
      `cp-kafka-rest:8.1.3`,
      `cp-enterprise-control-center-next-gen:2.5.0`, and
      `confluent-init-container:<operator-minor>` (currently `3.1.2`).
- [ ] **KeyFactor PKI ClusterIssuer reachable** if any CR uses
      cert-manager-issued TLS material. Owner: Rick.

## 1. Per-CR manifest review (every CR in `apps/confluent-platform/<env>/`)

Loop this section for each of: `kraftcontroller.yaml`, `kafka.yaml`,
`schemaregistry.yaml`, `connect.yaml`, `kafkarest.yaml`,
`controlcenter.yaml`, `kafkarestclass.yaml`. Plus the CMF CRs in
`apps/confluent-cmf/<env>/`.

### 1a. Identity / scope
- [ ] `metadata.namespace: dah-flink-<env>`
- [ ] `metadata.labels` includes the FCB common-metadata set:
      `app.kubernetes.io/{name,instance,component,part-of}`,
      `fcbint.net/app-id: "11547"`
- [ ] `spec.injectLabels` carries the same FCB common-metadata
      (this labels the auto-generated StatefulSet)
- [ ] `spec.podTemplate.labels` carries the same FCB common-metadata
      *and* (where applicable) the `cfk-role` anti-affinity label
      (this labels the Pod inside the StatefulSet —
      `LESSONS_LEARNED.md` A7)

### 1b. Image alignment
- [ ] `spec.image.application` matches the env's pinned cp-* tag
      (currently `8.1.3`); C3 uses cp-enterprise-control-center-next-gen
      on its own version line (currently `2.5.0`)
- [ ] `spec.image.init` matches the deployed operator's CFK minor
      (currently `3.1.2`); see `LESSONS_LEARNED.md` D1
- [ ] All image references use the `artifactory.fcbint.net/...` prefix —
      no `docker.io`, no `quay.io` direct pulls

### 1c. OAuth / OIDC configuration (every component except KRaftController)
- [ ] `scope: 11547.DAH(<EnvName>)` matches the env (Dev, UAT, STG,
      PRD-1, PRD-2 — capital case as defined in Okta)
- [ ] `groupsClaimName: dah<Env>_groups` matches the env (dahDev_groups,
      dahUAT_groups, etc.)
- [ ] `subClaimName: sub` (consistent across envs)
- [ ] OAuth config uses the *nested* `authentication.oauth.{secretRef,
      configuration}` shape, not the flat form
      (`LESSONS_LEARNED.md` A6)
- [ ] For ControlCenter only: top-level `authentication.type` is
      `mtls` with `sslClientAuthentication: requested`, and OIDC is
      configured under `dependencies.mds.ssoProtocol: oidc`
      (`LESSONS_LEARNED.md` A5)

### 1d. Resources, scheduling, and admission constraints
- [ ] `spec.podTemplate.resources` (NOT `spec.resources`) is set;
      requests and limits both present (`LESSONS_LEARNED.md` A1)
- [ ] Per-CR resources budgeted against the namespace ResourceQuota,
      remembering the ~500m init-container floor
      (`LESSONS_LEARNED.md` A3 / F1)
- [ ] `spec.podTemplate.podSecurityContext: {}` is set (lets OpenShift
      restricted-v2 SCC assign UID from namespace range —
      `LESSONS_LEARNED.md` E1)
- [ ] `spec.pdb: { enabled: true, maxUnavailable: 1 }` is present
      (`LESSONS_LEARNED.md` B1)
- [ ] `spec.podTemplate.probe.{liveness,readiness}` present with
      env-appropriate timing (no `startupProbe` exists in the CRD —
      `LESSONS_LEARNED.md` A2 — accept the `[startup]` warning)
- [ ] PodAntiAffinity matches the cfk-role label for the
      multi-replica StatefulSets (Kafka brokers, KRaft controllers,
      Connect workers, SR replicas) so they spread across nodes

### 1e. Replicas vs env topology
- [ ] `spec.replicas` matches the env's VM topology *and* fits within
      the namespace ResourceQuota
- [ ] In dev specifically: ControlCenter and Connect are at `replicas:
      0` (suspended) until Tom raises the quota; revert when he does
      (`LESSONS_LEARNED.md` F1)
- [ ] In upper envs: C3 at `replicas: 2` for HA, Connect at `replicas:
      2` matching VM, SR at `replicas: 2`, KRaft at `replicas: 3`,
      Kafka brokers at the env's VM count

### 1f. Dependencies (bootstrap, MDS, SR endpoints, KafkaRestClass)
- [ ] `dependencies.kafka.bootstrapEndpoint` uses the in-cluster
      service DNS for the target env:
      `kafka.dah-flink-<env>.svc.cluster.local:9092`
- [ ] `dependencies.mds.endpoint`:
      `https://kafka.dah-flink-<env>.svc.cluster.local:8090`
- [ ] `dependencies.schemaRegistry.url`:
      `https://schemaregistry.dah-flink-<env>.svc.cluster.local:8081`
- [ ] `dependencies.kafkaRestClassRef.name: default` and namespace
      matches
- [ ] KafkaRestClass CR (`kafkarestclass.yaml`) is present and points
      at the env's Kafka CR

### 1g. ExternalSecret manifests
- [ ] Each ExternalSecret resolves to an RFC1123-safe Kubernetes object
      name (`LESSONS_LEARNED.md` C4)
- [ ] CyberArk webhook URLs have spaces encoded as `%20`
      (`LESSONS_LEARNED.md` C3)
- [ ] CyberArk safe in the URL matches where the record actually lives
      — confirm with Walter / Tushar (`LESSONS_LEARNED.md` C2)
- [ ] License-bearing ExternalSecrets follow the consumer's expected
      format: CMF wants raw JWT, CFK Kafka wants `license=<JWT>`
      (`LESSONS_LEARNED.md` C1)
- [ ] Pipeline waits on `Ready=True` (not just secret existence)
      before proceeding

## 2. Apply order (don't skip steps; CFK dependencies are real)

CFK does its own dependency wiring through the operator, but applying
in a sane order avoids transient "X waiting for Y" loops that take
minutes to clear. The `confluent-platform.yaml` pipeline encodes the
phased order below — these checkboxes mirror what the pipeline does
so a manual recovery follows the same shape.

> **Targeted upgrades**: the install action exposes per-component
> checkboxes (KRaft Controller / Kafka Broker / Schema Registry /
> Kafka Connect / Kafka REST Proxy / Control Center). All default
> to checked — a plain install run applies everything as before.
> For a cluster upgrade, run the pipeline once per stage with only
> the components for that stage checked: kraft first, then kafka,
> then SR/Connect/REST in parallel, then C3. The pipeline still
> enforces the readiness gates between stages even when only one
> downstream component is selected.

1. [ ] All ExternalSecrets — wait for every one to report `Ready=True`
2. [ ] TLS secrets (KeyFactor cert-manager Certificates) — wait for
       `Ready=True` on the underlying Secret

**Phase 1 — apply, then wait for cluster-ready before phase 2:**

3. [ ] `kafkarestclass.yaml`
4. [ ] `kraftcontroller.yaml`
5. [ ] `kafka.yaml`
6. [ ] Wait for `kraftcontroller/kraftcontroller` to report
       `platform.confluent.io/cluster-ready=True`
       (up to ~15 min; pipeline polls every 10s)
7. [ ] Wait for `kafka/kafka` to report
       `platform.confluent.io/cluster-ready=True`
       (up to ~15 min)

> **Why the wait gate**: Schema Registry and other dependent pods
> hit `kafkastore.init.timeout.ms` (~60s) before Kafka brokers
> reach Ready and go into `CrashLoopBackOff`. Pod-level
> `initContainer` would fix this but CFK 3.1.x CRDs don't expose
> one. See `LESSONS_LEARNED.md` A14.

**Phase 2 — Kafka is up, dependents can come up safely:**

8. [ ] `schemaregistry.yaml`
9. [ ] `connect.yaml` and `kafkarest.yaml` (can be parallel)
10. [ ] `controlcenter.yaml`

## 3. Post-deploy verification

- [ ] All Pods `Ready 1/1` (or `2/2` if sidecars); no
      CrashLoopBackOff anywhere in the namespace
- [ ] No `FailedAdmission` events in the namespace
      (`oc get events --field-selector reason=FailedAdmission`)
- [ ] Each StatefulSet has a PDB; `kubectl get pdb` shows
      `ALLOWED-DISRUPTIONS` ≥ 1
- [ ] Every ExternalSecret reports `Ready=True`
- [ ] No `FailedMount` events (Ceph CSI healthy on every node holding
      a CFK pod)
- [ ] `kafka.dah-flink-<env>.svc.cluster.local:9092` reachable from a
      busybox pod in the namespace with the proper OAuth credentials
- [ ] Schema Registry `/subjects` returns 200 (or `[]` on a fresh
      cluster)
- [ ] ControlCenter UI loads and OIDC redirect goes through Okta cleanly
- [ ] MDS issues tokens on
      `https://kafka.dah-flink-<env>.svc.cluster.local:8090/security/1.0/authenticate`
- [ ] At least one round-trip producer/consumer through KafkaRest
- [ ] (For envs past dev) cluster link from VM CP is up and lagging
      within target bounds — confirm with Tushar

## 5. Known recovery commands

Quick-reference for problems that have a documented fix in
`LESSONS_LEARNED.md`. Run only after confirming the symptom matches.

- **Connect CR stuck in `Terminating` after `oc delete`** (E3) — only
  when the broker cluster was unhealthy at uninstall time, and the
  pods/StatefulSet are already gone:
  ```
  oc -n dah-flink-<env> patch connect connect \
    --type=merge -p '{"metadata":{"finalizers":[]}}'
  ```
- **Same pattern for any other CFK CR stuck in `Terminating`** — verify
  the underlying StatefulSet/pods are already gone first
  (`oc -n dah-flink-<env> get sts,pod -l app.kubernetes.io/instance=<name>`),
  then patch finalizers to `[]` as above with the right kind/name.
